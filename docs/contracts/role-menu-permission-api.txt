----------------------------------------------------------------------
SCREEN FLOW (like role-menu-permission.png)
----------------------------------------------------------------------
  1. Fill "Select Role"      : GET  /api/v1/roles
  2. Show the grid           : GET  /api/v1/roles/{roleId}/menu-permissions
  3. User ticks / unticks
  4. Submit                  : PUT  /api/v1/roles/{roleId}/menu-permissions
  5. Users of that role get the new menus at their next login or token
     refresh (POST /api/v1/auth/login, POST /api/v1/auth/refresh).

Grid columns
  #            = menu.access           (module checkbox: shows the menu)
  Module Name  = menu.title, and one row per menu.resources[].label
  Add          = resource.add
  Edit         = resource.edit
  Delete       = resource.delete
  View         = resource.view
  (extra)      = resource.actions[]   (e.g. Handle alerts, Send device
                                       commands, Send sensor readings)
  A null cell = the resource has no such operation: show no checkbox
  (the blank cells in the screenshot).

----------------------------------------------------------------------
SAFE-FARE ADMIN: NO TENANT IN THE TOKEN
----------------------------------------------------------------------
The Safe-Fare Admin logs in WITHOUT a tenantCode, so the token has no
tenant (user.tenantId = null, user.platform = true). Role permissions
belong to a tenant, so the admin chooses the tenant on every request
instead of in the token:

  X-Tenant-Id: <tenant id>        (header)            or
  ?tenantId=<tenant id>           (query parameter)

Screen flow for the admin (one extra "Select Tenant" dropdown):
  1. Login, no tenantCode   : POST /api/v1/auth/login
                              {"login": "...", "password": "..."}
  2. Fill "Select Tenant"   : GET  /api/v1/platform/tenants?status=ACTIVE
                              -> data[].id, code, name
  3. (optional) check it    : POST /api/v1/platform/switch-tenant
                              {"tenantId": 1}
                              -> {"tenantId": 1, "code": "Ganesh",
                                  "name": "Ganesh Travels",
                                  "header": "X-Tenant-Id"}
  4. Fill "Select Role"     : GET  /api/v1/roles
  5. Show the grid          : GET  /api/v1/roles/{roleId}/menu-permissions
                              X-Tenant-Id: 1
  6. Submit                 : PUT  /api/v1/roles/{roleId}/menu-permissions
                              X-Tenant-Id: 1
  Keep the selected tenant id in the UI (e.g. in memory / local storage)
  and send X-Tenant-Id with every call of this screen. Changing the
  tenant dropdown = reload the grid with the new X-Tenant-Id.

Without a tenant (no header, no ?tenantId=):
  GET / PUT menu-permissions -> 400 TENANT_REQUIRED
  {"code": 400, "msg": "Select a tenant (X-Tenant-Id header) for this operation",
   "data": null, "total": null,
   "extend": {"errorCode": "TENANT_REQUIRED", "fieldErrors": [], "requestId": "..."}}

Other tenant errors
  400 INVALID_TENANT        the tenant id does not exist or is not ACTIVE
  403 TENANT_ACCESS_DENIED  a tenant user sent another tenant's id
                            (tenant users never need the header: their
                            tenant always comes from their account)

Admin's own menus: the admin's login response "menus" contains every
menu, including the platform menus (Tenants, Global Roles, Permission
Catalog, Menus & Screens, Reference Data). They are never in the
role-permission grid, because tenant roles cannot get them.

----------------------------------------------------------------------
COMMON RULES
----------------------------------------------------------------------
Headers
  Authorization: Bearer <accessToken from POST /api/v1/auth/login>
  Content-Type : application/json            (PUT / POST requests)
  X-Tenant-Id  : <tenant id>   Safe-Fare Admin only (or ?tenantId=):
                 REQUIRED for this screen, see the section above.
                 Tenant users leave it out: they always work in their
                 own tenant (taken from the token).

Tenant
  Role definitions (ADMIN, OPERATOR, ...) are global; their permissions
  are per tenant. A save changes the role in ONE tenant only.

Permissions needed
  GET  menu-permissions : role.permission.read
  PUT  menu-permissions : role.permission.update
  GET  /roles           : role.read
  (ADMIN has all of these automatically.)

Every checkbox is a permission code
  Each cell has "permissionCode". The same code can appear on several
  menus; it is ONE permission, so all its checkboxes have the same
  state. When the user ticks or unticks one, tick / untick every cell
  with the same permissionCode. Shared codes today:
    device.read : Dashboard, Live Monitoring, Vehicles & Assets
                  (Vehicles > View), Fleet AI Assistant, Notifications,
                  Profile & Settings, Global Search
    alarm.read  : Alerts & Events (Alerts > View), Safety Analytics
    video.live  : Live Monitoring (action), Historical Video (action)
    driver.app  : all driver menus (My Work, My Shifts, ...)

Disabled checkboxes
  editable = false: show the checkbox but disable it. Reasons:
    - the role is ADMIN (full access by policy, never editable), or
    - the logged-in user does not have role.permission.update, or
    - the logged-in user does not hold that permission himself
      (nobody can give away a permission they do not have).

Module checkbox unticked
  When "#" (access) is unticked, untick and disable the other boxes of
  that menu in the UI. Note access is usually the same code as the
  first View box (e.g. Vehicles & Assets: device.read).

Response envelope (every API)
  {"code": 200, "msg": "Success", "data": ..., "total": null, "extend": null}

Error envelope
  {"code": 409, "msg": "<reason>", "data": null, "total": null,
   "extend": {"errorCode": "PROTECTED_ROLE", "fieldErrors": [],
              "requestId": "d4f263db-f089-4ea2-bd7b-cc8f36a3c7d3"}}

2. GET THE PERMISSION GRID OF A ROLE
======================================================================
GET /api/v1/roles/{roleId}/menu-permissions
Permission: role.permission.read

Path parameter
  roleId   long   from GET /api/v1/roles

Request examples
  GET /api/v1/roles/3/menu-permissions
  GET /api/v1/roles/3/menu-permissions      (Safe-Fare Admin)
      X-Tenant-Id: 1

Response fields (data)
  tenantId               long     tenant the grid belongs to
  roleId                 long
  roleCode               string   e.g. OPERATOR
  fullAccess             bool     true for ADMIN (everything ticked)
  editable               bool     false = whole grid read-only
  menus[]                         one per menu, in menu order
    menuId               long
    menuKey              string   e.g. vehicles_assets
    title                string   e.g. "Vehicles & Assets"
    icon                 string
    parentId             long|null
    sortOrder            int
    access               Cell|null  module checkbox (#); null = the
                                    menu needs no permission
    resources[]                     rows of the menu
      label              string   e.g. "Vehicles", "Device groups"
      view               Cell|null
      add                Cell|null
      edit               Cell|null
      delete             Cell|null
      actions[]          ActionCell  extra checkboxes (may be empty)
  otherPermissionCodes   string[] permissions of the role that no
                                  checkbox shows (e.g. own.data.read);
                                  kept unchanged when the grid is saved

  Cell        {"permissionCode": string, "granted": bool, "editable": bool}
  ActionCell  {"label": string, "permissionCode": string,
               "granted": bool, "editable": bool}

  granted  = the checkbox is ticked
  editable = the checkbox can be changed by the logged-in user

Platform-only screens (Tenants, Global Roles, Permission Catalog,
Menus & Screens, Reference Data) are never in the grid.

======================================================================
3. SAVE THE GRID (Submit)
======================================================================
PUT /api/v1/roles/{roleId}/menu-permissions
Permission: role.permission.update

Request body
  permissionCodes   string[]   required. The permissionCode of EVERY
                               ticked checkbox (module, view, add, edit,
                               delete and action boxes). Duplicates are
                               fine. Max 300.

How it is saved
  - Grid codes in the list         -> given to the role.
  - Grid codes NOT in the list     -> removed from the role.
  - otherPermissionCodes           -> kept unchanged.
  - Only the tenant of the caller (or X-Tenant-Id) is changed.
  - Recorded in the audit log (ROLE_PERMISSIONS_REPLACE).

Request example (OPERATOR: Dashboard and Vehicles view + add, Vehicle
registry view, Alerts view + handle)
  PUT /api/v1/roles/3/menu-permissions
  {
    "permissionCodes": [
      "device.read",
      "device.create",
      "vehicle.read",
      "alarm.read",
      "alarm.handle"
    ]
  }

Response 200
  The saved grid, same shape as GET (section 2), e.g.
  menus[vehicles_assets].resources[Vehicles].add.granted = true

Errors
  400 VALIDATION_FAILED  permissionCodes missing / too many
  400 INVALID_VALUE      a code that is not a checkbox of the grid,
                         e.g. "own.data.read" or a platform code
                         ("Not a checkbox of the menu grid: [...]")
  401 UNAUTHENTICATED
  403 FORBIDDEN          no role.permission.update, or the request
                         changes a permission the caller does not hold
                         ("You cannot grant or remove permissions you
                          do not hold: [...]")
  404 NOT_FOUND          unknown roleId
  409 PROTECTED_ROLE     roleId is ADMIN ("ADMIN has full access within
                         its tenant by policy; its permissions cannot be
                         edited")

4. LOGIN RESPONSE WITH MENUS
======================================================================
POST /api/v1/auth/login        (public)
POST /api/v1/auth/refresh      (public, same response)

Request (login)
  {"tenantCode": "Ganesh", "login": "user@example.com", "password": "******"}

  tenantCode: the user's tenant. Leave it out for the Safe-Fare Admin.

Request (refresh)
  {"refreshToken": "<refreshToken from login>"}

New field in the response: data.menus
  The menus this user can open, built from the role's permissions in the
  user's tenant, in menu order. Use it to build the sidebar and to
  show / hide buttons. Same as GET /api/v1/me/permissions -> screens.
  (The backend still checks the permission on every API call.)

  menus[]
    menuKey        string    e.g. vehicles_assets
    title          string
    routePath      string    e.g. /vehicles
    icon           string
    parentId       long|null
    readOnly       bool      true = only View is allowed on this menu
    resources[]              per resource of the menu
      label        string
      read         bool|null    View allowed   (null = no such operation)
      create       bool|null    Add allowed
      update       bool|null    Edit allowed
      delete       bool|null    Delete allowed
    operations[]             every operation of the menu
      operation      string  READ | CREATE | UPDATE | DELETE | ACTION
      permissionCode string
      label          string
      allowed        bool

After a role change
  The user's current token keeps the old permissions until it expires
  (expiresIn, 15 minutes). Call POST /api/v1/auth/refresh (or log in
  again) to get the new permissions and menus.

Errors
  400 VALIDATION_FAILED     login / password / refreshToken missing
  401 INVALID_CREDENTIALS   login: wrong tenant code, login or password,
                            or the user is not active
  401 INVALID_TOKEN         refresh: unknown, revoked or expired
                            refresh token
